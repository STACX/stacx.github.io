How to Contribute

How to contribute to STACX, key architectural design decisions, and validation experiments.

1 Module Roadmaps

Detailed development trajectory for each framework pillar, showing how capabilities evolve across phases. Each module below maps directly to contribution areas in Section 2.

Training Engine

rl_engine/trainer/ — Three-layer architecture: StacxTrainer → RoleWorkers → TrainBackend + ModelSpecialization

Phase 1

Foundation

  • Dual-backend architecture: Megatron-LM (TP/PP/DP/CP) and PyTorch FSDP v2
  • Weight sync to SGLang inference engines via inject (Ray) and exchange (NCCL)
  • Checkpointing & profiling infrastructure
  • Megatron-ARM backend for GH200 cluster support WIP
Phase 2

Scaling

  • Diffusion RL backend: DiffusionSpecialization with flow matching loss for DiT / MM-DiT architectures
  • Advanced parallelism strategies: Sequence Parallelism (SP), Context Parallelism (CP)
  • Elastic GPU scaling — dynamic worker addition/removal during training
  • Online reward model integration for real-time reward computation
  • Mid-scale validation: 7B–32B stable training for 1000+ steps
Phase 3

Production

  • 70B+ multi-node training with TP+PP+DP across 128+ GPUs
  • Multi-modal RL pipelines: joint image + text training
  • Automated hyperparameter sweep infrastructure
  • Throughput optimization targeting MFU ≥ 40%
  • Production monitoring & fault tolerance

Production

  • Cross-domain transfer learning recipes
  • Continuous evaluation with live leaderboard
  • Full benchmark coverage with per-domain tuned variants

2 Contribution Guideline

Each roadmap item has a natural entry point in the codebase. Below are the highest-impact contribution areas, organized by difficulty.

Single-subsystem contributions

Self-contained tasks that require understanding of one framework subsystem. Can be completed independently.

New Algorithm Recipe

Entry point: rl_engine/trainer/specialization/ + rl_engine/trainer/recipes.py

Adding a new RL algorithm to STACX requires two things:

  1. A ModelSpecialization subclass (~40 lines) — Implement compute_loss(), prepare_batch(), and extract_model_output(). The specialization encapsulates all algorithm-specific logic.
  2. An @recipe config function (~10 lines) — Returns a frozen TrainingConfig declaring which roles participate, how they synchronize data, and a description.

Only recipes.py and the new specialization change. The existing specializations in rl_engine/trainer/specialization/agent.py (diffusion variants in diffusion.py) are the reference implementations.

@recipe("my_algo")
def my_algo_config():
    return TrainingConfig(
        name="my_algo",
        description="My new algorithm",
        roles=(ModelRole(name="policy",
                         specialization_cls=MySpecialization),),
        syncs=(DataSync(source="value", target="policy",
                        keys=("values",), stage="inject"),),
    )

New Benchmark Environment

Entry point: rl_engine/examples/

Integrate a new benchmark by providing the two pieces the existing examples use:

  • A Harbor-style task directory — the task instances and their assets
  • An evaluator_config.py — wires the agent, environment, and reward for the run

Wire it into the composable Evaluator pipeline (Agent + Environment + Reward). The SWE-bench integration in rl_engine/examples/swe_agent/ is the best reference. Math benchmarks (WeMath, MathVision) are the lowest-complexity next targets — they need only string-match verification with no sandbox.

Scheduling Strategy

Entry point: rl_engine/rollout/scheduler/

The current TaskScheduler uses FIFO batching. The next targets are:

  • Priority-based scheduling — Assign priorities to task types (e.g., math > coding > eval) so high-value rollouts get GPU time first
  • Fair-share scheduling — Ensure each task type gets proportional GPU time in heterogeneous workloads
  • Adaptive batching — Dynamically adjust batch sizes based on evaluator throughput and pending queue depth

The batching strategy is a plain function — the default is fifo_batching in rl_engine/rollout/scheduler/task_scheduler.py — passed to TaskScheduler; supply a new function to change the policy. The scheduler is decoupled from the rollout manager, so new strategies can be tested without modifying the inference pipeline.

Browser / Terminal Environments

Entry point: rl_engine/examples/

Extend the environment engine to support interactive tasks:

  • WebArena — Docker container with headless Chromium. The agent navigates web pages, fills forms, and completes user workflows. Requires screenshot capture and DOM extraction for observations.
  • Terminal-Bench — Shell sandbox with configurable tool access. Reward function based on exit codes and diff-based correctness checks. Lower complexity than browser environments.

Both environments use the same Agent + Environment + Reward evaluator pipeline. The sandbox infrastructure from SWE-bench can be reused for process isolation and resource limits.

Training & rollout contributions

Require deep understanding of the training or rollout subsystems.

Diffusion RL Pipeline

Entry point: rl_engine/trainer/specialization/diffusion.py

Complete the end-to-end diffusion model RL pipeline. This spans both the trainer and rollout subsystems:

  • Backend: Finish DiffusionSpecialization (recipe diffusion_rwfm, reward-weighted flow matching) — production-grade diffusion data loading, noise schedule integration, velocity field extraction
  • Rollout: Build the iterative denoising inference pipeline in SchedulerRolloutManager — multi-step generation, noise scheduling at inference time, weight sync for diffusion checkpoints
  • Validation: End-to-end training on a DiT model, evaluated on GenEval2 and DPG-Bench

Requires familiarity with flow matching / weighted scoring loss formulations and DiT / MM-DiT architectures (e.g., Stable Diffusion 3, FLUX).

World Model & Video Model RL

Entry point: rl_engine/trainer/specialization/

Extend the specialization system to support world models and video generation models for RL training. This involves:

  • New ModelSpecialization subclasses for autoregressive video prediction and world-model rollouts
  • Temporal sequence handling in the rollout pipeline (multi-frame generation, state prediction)
  • Reward formulation for video quality and physical plausibility

The existing diffusion RL infrastructure provides the foundation. Extends naturally to video generation (frame-by-frame denoising) and world models (latent state prediction).

Vision-Language RL

Entry point: rl_engine/trainer/specialization/agent.py + rl_engine/rollout/

Extend the actor specialization to handle vision-language model inputs (image + text tokens in the same rollout batch). Requires:

  • Multi-modal input handling in prepare_batch() for vision encoders
  • VLM-compatible rollout data format in the scheduler
  • Validation on visual benchmarks (MathVision, MME-RealWorld-Lite)

Cross-subsystem contributions

Work that spans the trainer, rollout, and environment subsystems.

Large-Scale Coding Agent Training

Entry point: Full stack — trainer, rollout, and environment

The Phase 3 flagship goal: train a SOTA coding agent for top-tier SWE-bench performance. This requires:

  • 70B+ model training on 128+ GPUs with multi-turn agentic rollout
  • Coding-agent-specific reward shaping and curriculum learning
  • Multi-node SGLang inference for long-context code generation
  • Iterative self-improvement loops with debugging and test execution feedback

Combines all framework components at production scale.

Multi-Node Training Infrastructure

Entry point: rl_engine/trainer/backends/ + rl_engine/trainer/infra/

Scale the trainer to 70B+ models across multi-node clusters:

  • Advanced parallelism strategies (sequence parallel, context parallel) in the Megatron backend
  • Elastic GPU scaling — add/remove training workers without full restart
  • Fault tolerance and checkpoint recovery from mid-run failures
  • Throughput optimization targeting MFU ≥ 40% on 70B models

3 Key Design Decisions

Architectural choices that shape STACX. For full details, see the Architecture, Backends, and Rollout documentation.

Dual-Backend Trainer

Algorithms written against the shared TrainBackend interface run on both FSDP (1–4 GPU prototyping with HuggingFace models) and Megatron (production-scale TP+PP+DP) without changes.

Declarative Algorithm Recipes

Algorithms are expressed as data, not code. The trainer reads the recipe and automatically wires up the correct roles, syncs, and specializations. This is why adding a new RL algorithm takes ~50 lines: define the loss function and declare the training topology.

Unified Rollout Manager

Design

The same SchedulerRolloutManager + PlacementPool serves both LLM token generation and diffusion iterative denoising. Scheduling strategies are pluggable: currently FIFO, with priority-based and fair-share strategies planned.

The rollout manager owns all inference GPU allocation through PlacementPool. After each training step, weights are synchronized to the inference backend (SGLang for LLMs, denoising pipeline for diffusion). The scheduler batches requests and routes them to available inference workers, decoupling the training loop from inference throughput.

Composable Evaluator Pipeline

The composability means that the same Agent (e.g., a custom Agent handler with tool use) can be paired with different environments and reward functions without code changes; multiple tasks can be mixed in a single training run through the TaskScheduler.

Diffusion RL (DiT / MM-DiT)

Backend perspective

DiffusionSpecialization (recipe diffusion_rwfm) implements reward-weighted flow matching loss for DiT and MM-DiT architectures. Plugs into the same TrainBackend interface as LLM specializations, reusing RoleWorker pools, weight sync, and checkpointing infrastructure.

Rollout perspective

Diffusion-aware inference pipeline with iterative denoising steps, noise scheduling, and velocity field extraction. The rollout manager handles generation requests through the same TaskScheduler and PlacementPool used for LLM inference, ensuring unified resource management.

Interface and loss formulation defined in rl_engine/trainer/specialization/diffusion.py. Pending: production-grade diffusion data loading, noise schedule integration, and end-to-end validation on GenEval2 / DPG-Bench.

4 Validation Experiments

Experiments to validate STACX against established baselines and push new capabilities. Each experiment targets a specific roadmap phase.

LLM RL on Math Phase 2

Objective

Reproduce and extend published DAPO / GRPO results on math benchmarks (WeMath, MathVision). Validate the training pipeline at mid-scale (7B–32B models).

  • Target models: Qwen3-0.6B, Qwen3-4B, Qwen-2.5-Math-7B
  • Algorithms: GRPO, DAPO, PPO
  • Benchmarks: WeMath (6,500+ problems), MathVision (3,040 problems)
  • Success criteria: Match published DAPO-Math accuracy within 2% on Qwen-7B over 500 rollouts

LLM RL on SWE Phase 1–3

Objective

Train a state-of-the-art coding agent on SWE-bench with multi-turn agentic rollout and sandboxed code execution. This is the flagship production target.

  • Target models: Qwen-2.5-Coder-32B, 70B+ models at production scale
  • Algorithms: GRPO with coding-agent-specific reward shaping
  • Benchmarks: SWE-bench (2,294 tasks), LiveCodeBench (400+ problems), CodeContests (13,328 problems)
  • Success criteria: Top-tier SWE-bench resolution rate with multi-turn agentic rollout
  • Current status: SWE-bench environment integrated

Diffusion RL on Text-to-Image Phase 2

Objective

Train DiT/MM-DiT models with RL using weighted scoring matching loss. Validate generation quality improvements over base models.

  • Target models: FLUX-dev, Stable Diffusion 3
  • Algorithms: Weighted scoring diffusion RL
  • Benchmarks: GenEval2 (553 prompts), DPG-Bench (1,065 prompts)
  • Success criteria: Measurable GenEval2 score improvement over base model; reproducible baseline on DPG-Bench
  • Current status: Interface defined, pending production pipeline

LLM RL on MLE Phase 1–2

Objective

Machine learning engineering tasks with GPU sandbox environments, long-running code execution, and iterative debugging loops.

  • Target models: Qwen-2.5-Coder-32B
  • Algorithms: GRPO, PPO
  • Benchmarks: MLE-bench (75 Kaggle competitions)
  • Success criteria: Bronze medal equivalent on 3+ competitions; stable 1h+ GPU sandbox trajectories
  • Current status: MLE-bench environment integrated

Scaling Stages

All experiments progress through two scaling stages:

  1. Mid-scale training — 7B–32B models on 16–64 GPUs with GRPO/PPO on math + code tasks
  2. Full-scale deployment — 70B+ models, multi-node TP+PP+DP, heterogeneous task mixes across hundreds of GPUs
